## 1. מטרת העל והעיקרון המנחה

אנחנו בונים **בסיס אחד משותף** לכל האימונים וההצעות באפליקציה, במקום לוגיקה משוכפלת בין המפה, דף הבית, מסך אחרי-האימון וההתראות.

ארבעה עקרונות שמכתיבים כל החלטה במסמך:

1. **הפרדת אחריות** — מי שבונה אימון לא יודע איפה הוא יוצג ולמה נבחר. מי שמחליט מה להציע לא יודע איך אימון נבנה מבפנים.
2. **מקור אמת יחיד** — אותו מנוע החלטות מזין את כל המשטחים. ההבדל היחיד ביניהם הוא פרמטר הקשר אחד (`surface`) וסוג הטריגר.
3. **שיפור מקומי מתפשט גלובלית** — כשמדייקים חתיכה אחת (למשל טבטה), התיקון מחלחל אוטומטית לכל מקום שמשתמש בה. זהו מבחן התקינות של הארכיטקטורה.
4. **מנוע אחד, הרבה רגעים** — המנוע עונה גם ביוזמת המשתמש (pull) וגם בתגובה לאירוע בעולם האמיתי (push). אותו חוזה, אותו מוח — רק טריגר ומשטח שונים.

## 2. מפת השכבות

הזרימה: בריכות תוכן (חומר גלם) → שיטות ביצוע (איך מסדרים) → מחוללי אימון (אימון שלם) → מנוע ההצעות (בוחר מה להציע, בכל משטח ובכל רגע). הפלט חוזר ומזין את ההקשר דרך לולאת משוב.

```
בריכות תוכן ─┐
             ├─→ מחוללי אימון ─→ מנוע ההצעות ─→ [PULL] מפה / דף בית → אימון היום / תוכניות המשך
שיטות ביצוע ─┘                                ├─→ [PUSH] סיום אימון → התאוששות / משלים
                                              └─→ [PUSH] אירוע בזמן אמת → מיקרו-רגע (אזור התראות חמות)

מיקרו-רגע + אחרי-אימון ──(צעדים / פעילות)──→ UserContext ──(לולאת משוב)──→ מנוע ההצעות
```

## 3. סוגי הצעות ומצבי הפעלה

### 3.1 ארבעה סוגי הצעה (`Suggestion.type`)

| סוג | מתי | דוגמאות |
|---|---|---|
| `daily_workout` | ההצעה החכמה להיום | אימון מלא בפארק, כוח, טבטה |
| `post_workout` | מיד אחרי אימון | התאוששות, אימון משלים קצר, בטן |
| `program_recommendation` | המלצה לתוכנית רב-שבועית | עמידת ידיים, גמישות / שפגט |
| `micro_nudge` | אימון רגעי בזמן אמת | מדרגות, רד תחנה מוקדם, מתיחות משרד |

### 3.2 שני מצבי טריגר

- **Pull (ביוזמת המשתמש):** פותח מפה / דף בית / דף פארק → `daily_workout`, `program_recommendation`.
- **Push (מונע-אירוע):** סיום אימון → `post_workout` · אירוע בעולם האמיתי (תחבורה, מקום, שעה) → `micro_nudge`.

שני המצבים רצים על אותו מנוע ואותו `UserContext`. ההבדל הוא רק מה מפעיל אותו ולאן הפלט יוצא.

## 4. החוזה המשותף (הדבר שנבנה ראשון)

החלק הקריטי ביותר. אם הוא מדויק — כל השאר מתחבר אליו בקלות.

### 4.1 UserContext — כל מה שהמנוע צריך כדי להחליט

| שדה | תיאור |
|---|---|
| `userId` | מזהה המשתמש |
| `baseLevel` + `domainLevels` | רמת בסיס + רמה לכל דומיין (משיכה, דחיפה, רגליים, ליבה…) |
| `weeklyPerformance` | אילו דומיינים אומן השבוע, נפח, אילו אימונים הושלמו |
| `recoveryState` | מצב פריודיזציה (detraining / build), פער ימים, חלונות התאוששות |
| `todayGoal` | יעד היום (כוח / ריצה / ליבה / התאוששות אקטיבית) |
| `stepGoal` + `stepsToday` + `stepsRemaining` | יעד צעדים יומי, כמה נצברו, כמה חסרים |
| `preferences` | העדפות כלליות, אימוני ערב, רמת קושי מועדפת |
| `questionnaires` | אילו שאלונים הושלמו (למשל שאלון ריצה) ומה הם פותחים |
| `location` | GPS נוכחי, פארקים בקרבת מקום, ליד ספורטק, מרחק לפארק |
| `timeOfDay` | שעה ביום (מזין העדפת אימון ערב + חלון צהריים במשרד) |
| `surface` | מאיפה הבקשה: `map` / `home` / `park_page` / `post_workout` / `nudge` |
| `venue` | סוג המקום הנוכחי: משרד / בית / תחנת תחבורה / פארק |
| `transitState` | מצב תחבורה בזמן אמת (באוטובוס / ירד מרכבת) — אינטגרציית Moovit |
| `workdayState` | האם באמצע יום עבודה (לחלון המיקרו של הצהריים) |
| `buildingContext` | מדרגות/מעלית, מספר קומות — *עתידי רחוק* |
| `activitySignal` | זיהוי תנועה בזמן אמת (הליכה / עמידה / נסיעה) |

### 4.2 Suggestion — מה שכל מחולל פולט וכל מנוע מדרג

| שדה | תיאור |
|---|---|
| `id` | מזהה ההצעה |
| `type` | `daily_workout` / `post_workout` / `program_recommendation` / `micro_nudge` |
| `generatorId` | איזה מחולל יצר אותה |
| `title` / `subtitle` | תווית תצוגה (למשל "אימון מלא בפארק · הליכה + תחנת כוח") |
| `structure` | חימום / מקטעים / שחרור, משך בדקות, מספר סטים |
| `methodsUsed[]` | אילו שיטות ביצוע נכללות |
| `difficulty` | D1 / D2 / D3 |
| `goalTags[]` | אילו יעדים ההצעה משרתת |
| `stepContribution` | אומדן צעדים/פעילות שההצעה מוסיפה (מזין את לולאת המשוב) |
| `surfaceEligibility` | באילו משטחים ההצעה יכולה להופיע |
| `requiresLocation` | האם דורשת הקשר מיקום (למשל ליד ספורטק / ליד מדרגות) |
| `score` + `scoreBreakdown` | הציון שהמנוע נתן + פירוק לגורמים (לשקיפות ותיקון) |

## 5. שכבה 1 — בריכות תוכן

חומר גלם. כל בריכה = רשימה מתויגת של פריטים עם מטא-דאטה: דומיין, רמה, ציוד נדרש, זמן.

| בריכה | סטטוס | לדייק |
|---|---|---|
| תרגילי כוח | קיים | — |
| וריאציות בטן | קיים | — |
| סרטוני טבטה פולואו-אלונג | קיים | **איפה** הם נכנסים בתוך האימון (מיקום במקטעים) |

**חוזה הבריכה:** כל פריט נושא תגיות דומיין + רמה + ציוד, כדי ש-ParkGating והמחוללים יסננו נכון.

---

## 6. שכבה 2 — שיטות ביצוע

שיטה = **איך** מסדרים סטים או זמן. שיטה אינה אימון שלם; היא נשלפת על-ידי מחולל ומיושמת על תרגילים מהבריכה.

### 6.1 ממשק השיטה (Method)

```
Method {
  id, name
  appliesTo        // אילו דומיינים / סוגי תרגיל
  params           // פרמטרים ייחודיים לשיטה
  buildSets(exercises, params) -> StructuredSets
  renderActive()   // איך זה נראה באימון הפעיל
  renderPreview()  // איך זה נראה בדף מבט האימון
}
```

### 6.2 חוזה התצוגה הכפולה (חובה לכל שיטה)

כל שיטה **חייבת** להגדיר את עצמה בשני מצבים — זה ה"צריך לדייק איך הם בנויים":

- **אימון פעיל** — טיימרים, מוני חזרות, מנוחות, קיואים בזמן אמת.
- **דף מבט האימון** — שורת סיכום, אייקון, מבנה צפוי לפני שמתחילים.

תצוגה חסרה באחד המצבים = השיטה לא הושלמה.

### 6.3 מלאי השיטות

| שיטה | סטטוס | פרמטרים עיקריים | לדייק |
|---|---|---|---|
| סופר-סט | קיים | זוג תרגילים אנטגוניסטים | — |
| פירמידה | קיים | סכמת חזרות עולה/יורדת | תצוגה בפעיל + מבט |
| סטים שיא | קיים | אחוז/עומס סט שיא | תצוגה בפעיל + מבט |
| AMRAP | חסר | `timeCapMin` | לבנות מאפס |
| EMOM | חסר | `minutes`, `repsPerMin` | לבנות מאפס |
| אינטרוולים | חסר | `work`, `rest`, `rounds` | לבנות מאפס |
| שיטת משרד | חסר | מתיחות/תנועה קצרה בלי ציוד | לבנות מאפס |

## 7. שכבה 3 — מחוללי אימון

מחולל מרכיב בריכה + שיטות לאימון שלם. לא יודע איפה יוצג ולמה נבחר — רק בונה.

### 7.1 ממשק המחולל (Generator)

```
Generator {
  id, name
  eligible(context) -> bool          // האם ניתן להריץ בהקשר הנוכחי
  generate(context) -> Suggestion    // בונה אימון שלם מבריכה + שיטות
  surfaces                           // באילו משטחים רלוונטי
}
```

### 7.2 מלאי המחוללים

| מחולל | סטטוס | הערות |
|---|---|---|
| הליכה / מסלול | קיים | בונה מסלול על המפה |
| כוח מלא | קיים | קורא את מה שיש בדף הבית |
| טבטה | קיים | לדייק כשיטה/מחולל מבודד (מבחן הארכיטקטורה) |
| AMRAP היברידי | עתידי | תלוי בשיטות AMRAP + אינטרוולים; מזהה ספורטק, בונה סבב ריצה + כוח |
| ריצה | לא תפור | העבודה הגדולה ביותר; נבנה אחרון |
| אימון משרד | חסר | סשן מתיחות/תנועה קצר לחלון הצהריים (משתמש בשיטת משרד) |
| מיקרו-מחוללים | חסר | עליית מדרגות, רד-תחנה-מוקדם — ראה שכבת הרגעים |

## 8. שכבה 4 — מנוע ההצעות (מצב PULL)

מוח אחד. מקבל `UserContext`, מחזיר רשימת `Suggestion` מדורגת. הכי גבוה = "המומלץ", השאר = אלטרנטיבות. משרת את כל המשטחים דרך `surface`.

### 8.1 מודל הדירוג (מדרג חוקים משוקלל — לא ML בשלב זה)

| גורם | מה הוא בודק |
|---|---|
| התאמת יעד | האם ההצעה מקדמת את `todayGoal` |
| מילוי חוסר | להעדיף דומיין שלא אומן השבוע; להימנע מעומס-יתר |
| פער צעדים | `stepsRemaining` גבוה → בוסט להצעות עם מקטע הליכה; היעד הושג → כוח טהור |
| התאמת העדפות | העדפות כלליות, אימון ערב, רמת קושי |
| התאמת התאוששות | לכבד detraining / build / חלונות התאוששות |
| בונוס מיקום | ליד ספורטק → פתיחת ובוסט ל-AMRAP היברידי |
| שעה ביום | ערב → הצעות מתאימות · צהריים במשרד → חלון מיקרו |
| נעילות | ריצה מוצעת רק אם שאלון הריצה הושלם |

### 8.2 שילוב יעד-הצעדים (בידול)

יעד הצעדים הוא **קלט דירוג ממדרגה ראשונה**, לא נתון נלווה: הכרטיס המומלץ נבחר גם לפי כמה צעדים נשארו לעמידה ביעד היומי. חיבור אורגני בין האימון למטרה היומית שאף מתחרה לא עושה.

## 9. שכבת הרגעים וההתראות החמות (מצב PUSH)

אותו מנוע, אותו חוזה — אבל מופעל על-ידי אירוע בעולם האמיתי במקום פתיחת אפליקציה, ומפיק `micro_nudge` או `post_workout`.

### 9.1 טריגרים

מקום (`venue` = משרד/תחנה) · תחבורה בזמן אמת (Moovit) · שעה (חלון צהריים) · סיום אימון · זיהוי תנועה (`activitySignal`).

### 9.2 משטח ייעודי — "אזור התראות חמות"

מעל המקום שבו מופיע כרטיס סיכום האימון, וגם דרך פוש. הכרטיס קצר: כותרת פעולה ("צא לעלייה במדרגות") → ובסיום מיקרו-סיכום ("כל הכבוד, עלית 40 מדרגות").

### 9.3 דוגמאות מיקרו-רגע

- יצא מרכבת/רכבת קלה → פוש "עלה במדרגות".
- באוטובוס (Moovit) → "רד תחנה אחת מוקדם כדי ללכת יותר".
- כניסה לבניין עם מעלית ומדרגות → "עלה במדרגות עם פוש"; בניין גבוה → "רד במעלית X קומות מתחת והשלם ברגל". *(עתידי רחוק — תלוי בנתוני בניין)*
- צהריים במשרד → סשן מתיחות משרד קצר (מחולל אימון משרד + שיטת משרד).

### 9.4 לולאת המשוב (הלב של התוספת)

כל מיקרו-פעילות מזינה `stepsToday` / `activitySignal` חזרה ל-`UserContext`, וזה משפיע על ההצעה היומית. המדרגות של הבוקר מורידות את `stepsRemaining` — והמנוע מתאים בהתאם את אימון הערב. זו ה"שכבה מעל הכל שבהמשך משפיעה על האימון".

### 9.5 ממשל התראות (Nudge Governor) — חובה מוצרית

תקרת תדירות, קולדאון בין נדג'ים, ושעות שקטות — כדי שהמערכת לא תהפוך למטרד. בלי זה ה-push הופך את המשתמש לעוין.

---

## 10. סנכרון בין המשטחים

כל המשטחים קוראים לאותו מנוע עם אותו `UserContext`, ונבדלים ב-`surface` בלבד:

- סיים אימון כוח בפארק → דף בית → `post_workout`: משלים קצר או בטן, לפי מה שחסר וכמה זמן/צעדים נשארו.
- יש אימון ריצה היום → אותה הצעה זמינה גם במפה וגם בדף הבית.
- ליד ספורטק → הכרטיס ההיברידי עולה בדירוג אם מתחבר ליעד היום.
- ירד מהאוטובוס תחנה מוקדם → הצעדים נצברים → אימון הערב מתעדכן.

---

## 11. סדר בנייה מומלץ

1. **החוזה קודם** — `UserContext`, `Suggestion` (כולל `type`), ממשק השיטה, ממשק המחולל, חוזה התצוגה הכפולה.
2. **התאמת השיטות הקיימות** לחוזה + תצוגה כפולה: פירמידה, סטים שיא, סופר-סט.
3. **התאמת המחוללים הקיימים** לחוזה: הליכה, כוח מלא, טבטה (כולל מיקום סרטוני הפולואו-אלונג).
4. **בניית השיטות החסרות**: AMRAP, EMOM, אינטרוולים.
5. **בניית מנוע ההצעות (PULL)** כמדרג משוקלל; חיווט למפה + דף בית + אחרי-אימון.
6. **בניית המחולל ההיברידי (AMRAP)**.
7. **שכבת הרגעים (PUSH)** — מיקרו-מחוללים, אזור התראות חמות, לולאת משוב, Nudge Governor, אינטגרציית Moovit.
8. **מנוע הריצה** — נכנס כמחולל + שיטת אינטרוולים.
9. **שכבות חכמות בהמשך** — למידה/התאמה אישית מעל המדרג, בלי לשבור כלום.

## 13. חיבור למסמכי-האב הקיימים (03 — מוצר)

מסמך זה מפרט לרמת ספק-בנייה את מה שמסמכי החזון כבר קבעו ברמת חזון:

- **חזון מוצר v1.2** — ה-MOAT (אימון משולב מבוסס-מיקום), "עצירה גנרית", "נדנוד פרואקטיבי" (סעיף 4b), ופרוטוקולים (AMRAP/EMOM/superset/Tabata). שכבת הרגעים (סעיף 9 כאן) = המימוש של הנדנוד הפרואקטיבי.
- **יסודות וחזון חברתי v1.0** — עקרון ה-primitive האחד + target פולימורפי. חוזה ה-`Suggestion` כאן עקבי עם "אימון = יעד = אותה ישות".
- **OutRun — מנוע האימונים (Task Breakdown)** — שכבות זהות/תכנון/דריסה, תקציב נפח שבועי, ציון WHO. אלה מזינים ישירות את `UserContext` (`weeklyPerformance`, `recoveryState`) ואת מודל הדירוג.

## 14. שאלות פתוחות / החלטות עתידיות

- כיול משקלי הדירוג — להתחיל בערכים ידניים ולכוונן לפי נתונים אמיתיים.
- מנוע הריצה — היקף מלא — לתכנן בנפרד לאחר שהחוזה יציב.
- שכבת למידה/התאמה אישית — מתי ואיך להוסיף מעל המדרג הבסיסי.
- ממשל התראות — תדירות, שעות שקטות, הסכמת משתמש.
- אינטגרציות חיצוניות — Moovit (קרוב), נתוני מקום/בניין וקומות (רחוק) — לתעדף לפי בשלות.
- פרטיות והרשאות — מעקב מיקום/תחבורה בזמן אמת דורש consent מפורש.
- טיפול במצב "אין הצעה מתאימה" — ברירת מחדל בטוחה בכל משטח.
