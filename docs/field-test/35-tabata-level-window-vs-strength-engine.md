# 35 — טווח רמות לבחירת תרגילי טבטה (מול המסננת הקיימת), READ-ONLY

**תאריך:** 22.09.2026
**הקשר:** [[34-core-tabata-level-audit-and-block-cap]] מצא שמשתמש רמה 1 מקבל רק תרגיל core אחד →

## 1. איך מנוע הכוח מגדיר טווח רמות

`ContextualEngine.ts:113` — `const levelTolerance = context.levelTolerance ?? 3;` (ברירת מחדל
**±3**, ניתן לדריסה דרך `context`). מיושם ב-`ContextualEngine.ts:179-182`:

```ts
const effectiveLevelForTolerance = consistent.userLevel;
const minLevel = Math.max(1, effectiveLevelForTolerance - levelTolerance);
const maxLevel = effectiveLevelForTolerance + levelTolerance;
if (programLevel < minLevel || programLevel > maxLevel) { /* excluded */ }
```

חלון **סימטרי** (מתחת ומעל), שני הצדדים נמדדים מאותו domain (`resolveConsistentComparisonLevels`,
`workout-selection.utils.ts` — תוקן ב-08.09.2026 בדיוק כדי למנוע השוואה בין domain-ים שונים).
זה המסנן הכללי שכל בחירת תרגיל במנוע הכוח עוברת דרכו — לא ספציפי לליבה.

## 2. איך buildTabataFromPool/core-block מסננים היום

`tabata.block.ts:248-253`:

```ts
const atLevel = pool.filter(
  (ex) =>
    getIsometricTimeCap(ex) >= TABATA_CLASSIC.workSec &&
    poolLevelOf(ex) <= userLevel &&        // ← חד-צדדי, ללא סבילות
    passesInjuryShield(ex, injuryShield),
);
```

**תקרה חד-צדדית בלבד** — `poolLevelOf(ex) <= userLevel`. אין רצפה (תרגיל קל תמיד עובר) ואין
סבילות מעל הרמה (תרגיל אפילו רמה 1 מעל המשתמש כבר נפסל). זה שונה מהותית ממנוע הכוח: שם יש חלון
±3 משני הצדדים; כאן יש תקרה מדויקת בלי סטייה כלל. זה מסנן משותף לכל קורא ל-`buildTabataFromPool`
(דרך `buildTabataBlock`/`buildCoreTabataBlock`) — לא נגעתי בו בשום שלב.

## 3. עם אותו טווח ±3 — ספירה אמיתית (production, corePool=20)

רמות ה-corePool בפועל: `1,2,2,3,3,3,4,4,4,5,5,5,6,8,8,8,8,9,11,14`

| userCoreLevel | היום (תקרה, ללא סבילות) | עם ±3 (כמו מנוע הכוח) |
|---|---|---|
| 1 | **1** ❌ דק מדי | **9** ✅ מספיק לבלוק של 4 |
| 2 | 3 ⚠️ רק בלוק של 2 | **12** ✅ |
| 3 | 6 ✅ | 13 ✅ |
| 4 | 9 ✅ | 13 ✅ |
| 5 | 12 ✅ | 16 ✅ |

עם ±3, ברמה 1: החלון הוא `[max(1,1-3), 1+3] = [1,4]` — 9 תרגילים זכאים (כולל L2/L3/L4, לא רק
L1). ברמה 2: חלון `[1,5]` — 12 זכאים. **שני המקרים עוברים בנוחות את סף ה-4** שנדרש לתחנה
הטיפוסית (memberCount=4). מסקנה: טווח ±3 פותר את הבעיה שדוד זיהה, עם שוליים משמעותיים.

## 4. buildTabataFromPool משותף גם לטבטה-בטן הרגילה (מחוץ לתחנות)

**כן, אותו קוד בדיוק, אותו corePool בדיוק.** `WorkoutGenerator.ts` Step 6c בונה
`corePool = (context.tabataPool ?? []).filter(ex => hasExplicitCoreLevel(ex))` — זהה מילה
במילה לבנייה שלי ב-`dispatchStopContent`'s core branch. שניהם קוראים בסוף ל-`buildCoreTabataBlock`
→ `buildTabataBlock` → `buildTabataFromPool`, אותו מסנן `poolLevelOf(ex) <= userLevel`.

**כן, גם שם נופל היום, וזה לא תיאורטי:** `chooseCoreForm`'s `eligibleForms`
(`core-block.ts:121-124`) שוער **רק לפי זמן פנוי** (`headroom >= 4 דק'`) — **לא לפי רמת
המשתמש בכלל**. כל אימון רגיל (לא-היברידי) עם ≥4 דק' פנויות כשמגיעים לסלוט הליבה עלול לבחור
אקראית form='tabata' — גם למשתמש רמה 1. אם זה קורה, `buildCoreTabataBlock` נכשל (אותה סיבה
בדיוק — רק תרגיל אחד זכאי), והקוד עצמו מתעד את הנפילה:

```ts
// WorkoutGenerator.ts, Step 6c
} else {
  console.log('[CoreBlock] tabata composition failed — core stays form A (single)');
  coreForm = 'single';
}
```

כלומר: **זה באג קיים בפרודקשן היום**, בלתי-תלוי לחלוטין בעבודת התחנות שלי — משתמש רמה 1
שמזדמן לו form='tabata' בסלוט הליבה שלו כבר מקבל היום נפילה שקטה ל-single, בכל אימון רגיל, לא
רק בהיברידי. עבודת התחנות רק **חשפה** את זה, לא יצרה אותו.

**מה משתנה בכל אופציה:**
- **תיקון גלובלי** (בתוך `tabata.block.ts`, המסנן המשותף): מתקן את שני הנתיבים כאחד — גם
  התחנות החדשות וגם הטבטה-בטן הרגילה שכבר חיה בפרודקשן. משתמשים קיימים שהיו "רואים" נפילה שקטה
  יתחילו לקבל בלוק אמיתי — שינוי התנהגות אמיתי לתכונה חיה, לא רק לתכונה חדשה.
- **תיקון בתחנות בלבד** (רק בקריאה מ-`station-core-tabata.ts`, למשל דרך העברת `userLevel+3`
  כפרמטר לקריאה, בלי לגעת ב-`tabata.block.ts` עצמו): מתקן רק את מה שעדיין לא חשוף (המתג דלוק
  אבל זו תכונה חדשה) — הטבטה-בטן הרגילה נשארת עם הנפילה השקטה הקיימת, ללא שינוי.
