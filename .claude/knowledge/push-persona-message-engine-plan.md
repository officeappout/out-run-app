## המטרה

מערכת אחת מסודרת שבה **פרסונה, אימון והודעה תמיד מיושרים** — אף פעם לא "פרסונה אמא עם אימון אבא". עובדת גם **בלי פרסונה** (משתמש שלא השלים לוז/הרשמה מקבל הודעות טובות דרך fallback, לא נופל בין הכיסאות). מתחילים מ**פלואו שלם אחד מקצה לקצה — צעדים** — בודקים אותו על טלפון אמיתי, ורק אז מרחיבים.

---

## עיקרון הסדר — הסכימה שמונעת אי-התאמות

כל הודעה (פוש, כותרת אימון, תיאור אימון) נושאת את אותם תגים:

| שדה | ערכים | תפקיד |
|---|---|---|
| `category` | steps_50pct / steps_almost / steps_goal_hit / streak / comeback / onboarding_location / workout_title / workout_desc … | סוג ההודעה |
| `persona` | 8 הקנוניות **+ `generic`** (fallback) | קהל |
| `timeOfDay` | morning / midday / evening / any | רגע ביום |
| `framing` | gain / loss / neutral | מסגור |
| `copy` | טקסט עברית עם `{vars}` | הניסוח |
| `deepLink` | route / module / screen | לאן נוחת |
| `linkedWorkoutType` | walking / strength / running / none | לאיזה אימון קשור |

**הפרסונה הקנונית האחת** (מאמצים את רשימת ה-onboarding, `PersonaStep.tsx`, ומבטלים את 4 האחרות): parent / student / pupil / office_worker / reservist / soldier / vatikim / pro_athlete — **ועוד `generic`** כערך מן המניין.

### פונקציית בחירה אחת (בזמן שליחה) — כך נשמרת הקוהרנטיות
1. מזהים **טריגר** (למשל: 50% מיעד הצעדים היומי, 13:00).
2. **פרסונה** = `user.personaId`, ואם ריק → `generic`.
3. שולפים מועמדות שמתאימות ל־`category` + `persona ∈ {פרסונת המשתמש, generic}` + `timeOfDay`.
4. **בוחרים את הטובה ביותר** (מנגנון בסגנון `getBestMessage`, עדיפות + ניקוד).
5. ה־`linkedWorkoutType` של ההודעה שנבחרה קובע איזה אימון נבחר → הכותרת/תיאור שלו מוזרקים לקופי → ה-deep link מוביל לאותו אימון.

תוצאה: פרסונה ואימון מגיעים מ**אותה הכרעה אחת**; משתמש בלי פרסונה מכוסה ע"י `generic`; הודעת צעדים מקשרת **רק** לאימון הליכה.

## שלב 0 — בטיחות ויסודות (ראשון, זול, חשוב)

- להעביר את 3 השולחים שעוקפים את הבקרות דרך `push.service.ts` המשותף (שעות שקט, rate-cap, kill-switch).
- להוסיף **מתג-חירום גלובלי** אחד שעוצר את כל הפוש (לא קיים היום — סיכון תפעולי).
- לתקן את באג ה-deep-link של הצטרפות לקבוצה (`/community/groups/{id}` → `/community/{id}`, 404 היום).
- לאמץ **פרסונה קנונית אחת** ולמפות/לבטל את 4 האחרות.
- להגדיר `generic` כפרסונת fallback מן המניין.

## שלב 1 — פלואו שלם אחד מקצה לקצה: צעדים

הפרוסה האנכית שמוכיחה את כל התבנית:

- **טריגרים** (לא קיימים היום — לבנות): 50% מהיעד היומי, קרוב-ליעד, יעד-הושלם, רצף, החזרה.
- **כיוון** מודע-פרסונה, עם fallback ל-`generic`.
- **בחירת הודעה**: לחבר שכבת בחירה/ניקוד לפוש (הרחבת `getBestMessage` ל-FCM).
- **דיפלינק לאימון הליכה**: לבנות עמוד אימון-לפי-ID (לא קיים ציבורית היום) + בחירת אימון/מסלול בזמן שליחה.
- **קופי**: לזרוע את ספריית הצעדים (המטריצה שלנו + מאגר 201 ההודעות הקיים), פרסונה × רגע, מודע-אימון.
- **טסט על הטלפון של דוד**: לוודא גם עם פרסונה מלאה וגם בלי (fallback), שההודעה מובילה, שהמסלול נבנה, ושהפלואו הודעה→מסלול עובד.

## שלב 2 — לחדד ולהרחיב את ספריית הצעדים

- אחרי שהפלואו עובד: לייצר המון וריאציות (פרסונה × רגע × מסגור), להזריק בסקריפט.
- לסדר את **כותרות ותיאורי האימון** של כרטיס הצעדים באותה סכימה, שהכל (כותרת/תיאור/הודעה) מיושר.

## שלב 3 — להרחיב את התבנית לסוגי אימון נוספים

- אותה מכונה, תוכן חדש: כוח, ריצה. נדחה עד שהצעדים עובד.

## שלב 4 — בנייה גדולה (נדחה לסוף)

- פוש עם מסלול **שכונתי** (צריך שדה שכונה על המשתמש + עמוד מסלול).
- איחוד מנגנון ה-templating; להפוך את עורך התבניות בפאנל לאמיתי — או להסיר אותו (היום הוא מוק).

## הערות טכניות מהאודיט (נוספו 11.08.2026, לפני תחילת שלב 0)

1. **`vatikim` ≠ `senior`** — הרשימה הקנונית (onboarding) משתמשת ב-`vatikim`, אבל מאגר 201 ההודעות הקיים (`scripts/corpus/notification-corpus.json`) מתייג את אותה פרסונה כ-`senior` (31 רשומות). אם שלב 1/2 רוצים לזרוע מהמאגר הקיים — צריך מיפוי מפורש `vatikim ↔ senior`, אין התאמת מחרוזת אוטומטית.
2. **הרחבת `getBestMessage`** — כיוון נכון, אבל זו הרחבה אמיתית ולא שימוש-חוזר: `MessageService` היום קורא/כותב ל-`smart_messages` (client SDK, in-app בלבד), וה-priority שלו הוא מספר 1-10 ידני, לא חיזוי engagement. גרסת FCM צריכה query/collection חדשים, לא קריאה לפונקציה הקיימת עם audience חדש.
3. **מנגנון ה-deep-link** — ה-listener בצד לקוח עושה ניווט מלא (`window.location.href`) עם בדיקת same-origin בלבד, בלי allow-list נתיבים. תקין לשלב 1, אבל רלוונטי ברגע שיש deep link הניתן לעריכה ע"י אדמין. עמוד אימון-לפי-ID ציבורי **לא קיים היום מחוץ ל-`/admin`** — אושר בסבב המחקר, שלב 1 חייב לבנות אותו.
4. **ענף-לכל-שלב מול CLAUDE.md** — התוכנית מציעה ענף ייעודי לכל שלב; `CLAUDE.md` §Workflow קובע `עובדים ישר על main, בלי ענפי-פיצ'ר`. בפועל יש כיום ~17 worktrees מקבילים בריפו, כך שענפים ייעודיים כבר הנוהג בפועל — אבל זו סתירה ישירה לחוק כתוב, כדאי אישור חד-משפטי מדוד לפני שמתחילים, לא להניח.
