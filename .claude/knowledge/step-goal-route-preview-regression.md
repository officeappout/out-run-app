# Step-goal route-preview regression — investigation (inconclusive, flag reverted)

**12.08.2026.** David reported: tapping the step-goal push (sent with `IS_STEP_GOAL_ROUTE_PREVIEW_ENABLED=true` and `deepLink=/map?openRun=walking&targetSteps=2993`) landed on the home page instead of `/map`. Before that change (plain `openRun=walking`, no target, flag not existing yet), the same class of push correctly opened `/map`'s config drawer.

**Action taken**: reverted `IS_STEP_GOAL_ROUTE_PREVIEW_ENABLED` to `false` immediately (commit `9781697d`, pushed) per explicit fallback authorization, to restore the known-working state while diagnosis continues. **Root cause is NOT confirmed** — this file documents what was checked and ruled out, not a resolution.

## What I checked and ruled out

- **`global-error.tsx`** (Next.js root error boundary): does NOT redirect to home on any error. Shows an error page ("משהו השתבש") with retry, or for `ChunkLoadError` specifically, does `window.location.reload()` (same URL, not home). Ruled out as the direct mechanism — a genuine JS crash in the new code should have shown an error screen, not silently landed on home.
- **`src/app/map/page.tsx`** (the `/map` server component): reads only `workoutId`/`context`/`lat`/`lng` from `searchParams`; does not gate on or redirect based on `openRun`/`targetSteps` at all. Renders `MapShellEntry` unconditionally for any hit to `/map`. Not the redirect source.
- **`src/lib/native/push.ts`'s tap handler**: unchanged by any of my commits. Parses `deepLink` via `new URL(rawDeepLink, window.location.origin)`, confirms same-origin, does `window.location.href = target.href` — a full navigation. Standard `URL` parsing handles `?openRun=walking&targetSteps=2993` correctly; the `&` is not a special case. Confirmed this code path is untouched and should behave identically to before.
- **`src/app/page.tsx`** (the `/` splash/auth-gate): has no reference to `window.location.pathname`/`.search` anywhere — it does not read or restore an "intended destination" from the current URL. Its `redirectAfterAuth()` routes based on auth/onboarding state only, not on what URL triggered the app.
- **The concurrent session's own commits** landing on `main` in this window (`acf4d1a6`/`2f39eb30`, iOS thermal-state diagnostics) — confirmed via `git show --stat`: touch only `ios/App/App/ViewController.swift` and `src/lib/appForeground.ts`, zero overlap with map/routing code. Not the cause.

## What I could NOT rule out — unconfirmed hypotheses, ranked

1. **(Unconfirmed, moderate suspicion) Interaction with the pre-existing `[mapMode]`-keyed effect.** `DiscoverLayer.tsx` already had (before my changes): `useEffect(() => { if (mapMode === 'freeRun') setRouteCarouselConfig(null); }, [mapMode]);` — clears `routeCarouselConfig` back to `null` whenever `mapMode` transitions to `'freeRun'`. My new target-jump branch sets `routeCarouselConfig` non-null and `freeRunStep:'route'`. Traced the exact render/effect ordering by hand for both the same-tick case (GPS already resolved on mount) and the deferred case (GPS resolves later) — did not find a definitive race in either trace, but I was reasoning about React's effect scheduling from static code reading, not observing actual runtime behavior. This is the closest thing I have to a lead, not a confirmed bug.
2. **(Unconfirmed, low-moderate suspicion) Cold-launch timing.** If the app was fully killed (not backgrounded) before the tap, iOS launches the WebView fresh; the JS bundle must finish initializing and register `notificationActionPerformed` before it can handle the tap at all. If David's working test was on a warm/already-open app and this one was a cold launch, that's a different variable than my code change — but I have no way to know which state the app was in for either test, and David's framing ("same push... regressed") implies he doesn't believe launch-state was the variable either.
3. **(Considered, low suspicion) Next.js `useSearchParams()` static-generation/Suspense requirement.** `useSearchParams()` was already used for `initialOpenRun` before my change (not new), so this specific concern pre-dates my diff — unlikely to be newly triggered by adding a second `searchParams.get()` call, but I can't fully rule out a production-build-only static-analysis difference without seeing an actual Vercel build log, which I don't have access to.
