## Screen identity
"עריכת לוז" = **`TrainingPlannerOverlay`** (`src/features/home/components/TrainingPlannerOverlay.tsx`), mounted from `src/app/home/page.tsx:1452-1454`, opened via `setShowPlanner(true)` (`home/page.tsx:1266-1267`). Renders `MonthlyCalendarGrid` (`:355-368`) + `RollingAgenda` in `filterMode="planner"` (`:411-425`) **together, unconditionally, the instant the overlay opens**.

Confirmed NOT implicated: onboarding `ScheduleStep.tsx`/`RunningScheduleStep.tsx` (separate simple day-picker forms, untouched). Confirmed NOT implicated: Layer A (`scheduleRules.ts`) and Layer B (`useSmartSchedule`/`SmartWeeklySchedule`, home week-strip) — not imported anywhere in this render tree. The slowness is **intra-screen**, between the two sibling components `TrainingPlannerOverlay` mounts at once.

## Ranked findings (worst-first)

1. **N+1 read storm + read-then-write hydration cascade on every open — dominant cost.** `RollingAgenda.tsx:36-39,192-194` builds a 115-date window (30 past + today + 84 future); `:519-541` mounts one `AgendaDayCard` per date; each card's own effect (`AgendaDayCard.tsx:674-720`) calls `getScheduleEntries` → `getScheduleDay` → a single-doc `getDoc` (`userSchedule.service.ts:509-535`) = **115 concurrent Firestore reads**, no range query, despite docs storing `userId`+`date` fields that would support one `where('userId','==',uid).where('date','>=',start).where('date','<=',end)`. Worse: any empty date on a `recurringTemplate` day triggers `hydrateFromTemplate` (`userSchedule.service.ts:180-233`, 2nd read at `:197`) then `addScheduleEntry` (3rd read `:559` + `setDoc` `:579`) — **2 reads + 1 write per not-yet-materialized day**, fanned across ~30-50 cards for a typical user, all unbatched/no transaction. *Fix direction:* one range query for the window; batch-write hydration.

2. **Two sibling components fetch the same overlapping range independently, with a write race.** `MonthlyCalendarGrid.tsx:264-292` `Promise.all`s `getScheduleEntries` + conditional `hydrateFromTemplate` for ~28-31 current-month dates — the same `userSchedule/{uid}_{date}` docs `RollingAgenda`'s cards fetch, uncoordinated. Since `addScheduleEntry` (`userSchedule.service.ts:544-585`) is read-then-`setDoc` with **no `runTransaction`**, both components can race to hydrate the same empty day and each write a differently-`entryId`'d entry → **duplicate entries on the same day** (a correctness bug, not just perf). *Fix direction:* one shared fetch/cache hook instead of two independent service calls.

3. **Every mutation re-fetches the whole window, not just the changed day.** `TrainingPlannerOverlay.handleSaved` (`:236-239`) bumps `refreshKey` → `RollingAgenda` (`:419`) → `combinedRefreshKey` (`RollingAgenda.tsx:289`) → forwarded to **every** `AgendaDayCard` (`:538,583`), which lists it as an effect dep (`AgendaDayCard.tsx:720`) → all ~115 reads re-fire. Also reaches `MonthlyCalendarGrid` (`TrainingPlannerOverlay.tsx:365` → `MonthlyCalendarGrid.tsx:292`), re-fetching its ~30. **One edit ≈ 145 Firestore reads.** *Fix direction:* invalidate only the affected date(s) — mutation functions already know `fromDate`/`toDate`.

4. **No unified loading gate (perceived-perf symptom of #1).** Each of the 115 cards owns its own loading flag (`AgendaDayCard.tsx:649,677-678,746`) → overlay appears instantly but cards visibly trickle in one-by-one. Likely what "takes a long time" describes experientially.

5. **Minor.** `usePastWorkoutCompleted.ts:37-49` — one `getDoc` per past date in the current month (`dailyProgress/{uid}_{date}`), parallelized but still N round-trips vs one range query. Bounded, lower priority.

## Bottom line
Not a single slow query — it's **~115-145 uncoordinated Firestore round-trips per open/edit** from two components independently walking the same date range with per-day `getDoc`s instead of one ranged query, plus an unbatched read-then-write hydration path that also races (bug #2). Highest-leverage fix = replace the per-day `getDoc` loop in both `RollingAgenda`/`AgendaDayCard` and `MonthlyCalendarGrid` with a single ranged Firestore query per window, and scope `refreshKey` invalidation to the changed date instead of the whole window.
