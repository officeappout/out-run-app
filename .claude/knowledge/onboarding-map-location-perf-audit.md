## Screen identity
The onboarding "search for location" screen and the live map's "location-gate" overlay are **the same component**: `UnifiedLocationStep.tsx` (`src/features/user/onboarding/components/steps/UnifiedLocationStep.tsx`), used in 3 modes:
- `mode='onboarding'` (default) — mounted by `OnboardingWizard.tsx:320` for the `LOCATION` step of real registration (`/onboarding-new/...`). **No `AppMap`/`MapShell` involved.**
- `mode='bridge'` — mounted by `MapShell.tsx:823-828` as a z-[80] overlay when a logged-in user without `core.authorityId` opens `/map` directly (this is the "location-gate" `map-stability-oom.md` referenced at the old `:746` line).
- `mode='explorer'` — mounted by `src/app/explorer/page.tsx` for anonymous guests.

Not a lightweight decoy — it's a **full heavy component** (own Mapbox GL WebGL instance, production map style/declutter code) reused everywhere. Location-finding is user-initiated (tap "find my location" in `InitialCard.tsx:67`), not auto-fired on mount, so the complaint = what happens between that tap and the confirm screen.

## Ranked findings (worst-first)

1. **Fully sequential 4-network-call chain gates the loading spinner.** `UnifiedLocationStep.tsx:342-424` (`handleFindLocation`, same pattern in `handleDragEnd:285-340` and `handleCitySelect:533-609`): GPS (`:348`) → `await reverseGeocode` (`:373`) → `await findAuthorityIdByCity` (`:378`) → `await fetchHeroRoute` (`:389`) → `await fetchNearbyFacilities` (`:394`, calls `getAllParks()` internally). `LocatingCard` spinner stays up for the **full chain**. `fetchNearbyFacilities` has no data dependency on the authority/hero-route steps (only needs lat/lng) yet sits last — could run via `Promise.all` alongside steps 2-3. *Fix:* `Promise.all([geocodeAndHeroChain, fetchNearbyFacilities(lat,lng,...)])`.

2. **`getAllParks()` — whole national `parks` collection, zero caching, re-fired on every drag/city-pick.** `location-utils.ts:960-969` (`fetchNearbyFacilities`) → `parks.service.ts:97-106` (`getAllParks`): bare `query(collection(db,'parks'), orderBy('name'))`, no `where`/`limit`, no cache. Every debounced `handleDragEnd` (500ms) and every `handleCitySelect` re-runs the full-country fetch. Contrast with the live map's `fetchRealParks()` (`parks.service.ts:230-251`), which has localStorage + SWR caching — `getAllParks()` gets none of it. *Fix:* route through `fetchRealParks()`'s cache.

3. **Full Mapbox GL WebGL map mounted for what's functionally a pin-drop picker.** `UnifiedLocationStep.tsx:654-663` mounts `MapboxMap` unconditionally using the same production style (`MAPBOX_STYLE`, `location-constants.ts:11`) and runs the full ~150-layer declutter sweep `applyFitnessMapStyle` (`MapboxMapWrapper.tsx:46`) on load. Actual UI need = a draggable crosshair (`:866-946`) with ≤1 marker + 1 route line. Runs in parallel with the network chain, but competes for CPU/network/battery on a cold-start registration flow — pure excess weight. *Fix:* Mapbox Static Images API, or a stripped custom style (no buildings/POI/3D) for this step.

4. **Registration's parks fetch is thrown away and redone later.** Onboarding's `getAllParks()` (#2) only feeds local UI state; `handleConfirm` (`:470-526`) persists just a park name/rating, not the fetched list. When the user later opens `/map`, `AppMap.tsx:716` calls the entirely separate `fetchRealParks()` — its own cache, unrelated — **re-downloading the whole national parks collection again**. *Fix:* same as #2, one shared cache serves both call sites.

5. **(Live-map `bridge` mode only) Two simultaneous Mapbox GL instances during the location-gate.** `MapShell.tsx:684-696,812-829` — comment: "Map tree always mounts — Mapbox warms up behind the gate." `MapShellInner`/`AppMap` (full GL instance #1) and `UnifiedLocationStep mode="bridge"` (full GL instance #2) mount concurrently whenever `needsLocationGate` is true (`MapShell.tsx:712-721` — any hydrated profile lacking `core.authorityId`), sustained for the **entire gate duration by design**, not a brief transition like the free-run swap. Distinct from pure `/onboarding-new` registration, which never mounts `AppMap`. *Fix:* defer `MapShellInner` mount until the gate clears.

6. **Minor — redundant double Hebrew-label sweep.** `UnifiedLocationStep.tsx:222-234` schedules a 2nd `setMapLanguageToHebrew(map)` via `setTimeout(100)`, but `MapboxMapWrapper.tsx:41-53` already calls it synchronously on the same `onLoad`. No idempotency guard → full layer re-iteration twice. One-time cost, low severity. *Fix:* delete the redundant call.

7. **Checked, not a problem: GPS timeout/retry is sane.** `useGPSStore.ts:107` (native) / `:140` (web) — single `getCurrentPosition`, 10000ms timeout, no retry loop, no polling/backoff. Failure just returns to `INITIAL` card for manual retry. Not the classic silent-hang pattern.

## Bottom line
Root cause = a serial network chain (should be parallelized) stacked on an **uncached, whole-country parks query fired repeatedly** (every drag/city-pick, then discarded and re-fetched again on first real map open) — all inside a **full production Mapbox GL instance** that's overkill for a pin-drop picker. Highest-leverage fixes: parallelize the chain (#1), give `getAllParks()` the same cache `fetchRealParks()` already has, ideally unifying the two call sites (#2+#4).
